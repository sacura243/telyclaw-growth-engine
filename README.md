监控 X 上的账号 → 检测正在加速的话题 → 按「值不值得 TelyClaw 出手」排序 → 生成三个角度的草稿 → 人审批 → 发布 → 量 Qualified Engagement → 回写排序。

## 2. 一句话产品判断

**热点榜是廉价的，判断「哪个热点值得用 TelyClaw 的身份说话」才是产品。**

所以核心不是"抓到更多推文"，是四件事：

1. **排序要能解释。** 每个分数都能拆成五个因子加三个乘数，点开就能看到是哪一项把它推上去的。
2. **要有放弃。** 页面里专门有一块「我们主动放弃的」，写着为什么不做。只会推荐的东西等于没推荐。
3. **格式要分得开。** 同一个观点，单条、引用转发、长帖是三种不同的活。混在一起写，哪种都不合格。
4. **闭环要真的闭上。** 发布结果回写话题命中率，下一次排序会变——幅度只有 0.9×–1.1×，因为单条内容不该推翻整套判断。

### 2.1 为什么不直接用现成工具

| 现成方案 | 它解决什么 | 它不解决什么 |
|---|---|---|
| Typefully / Hypefury | 排期、线程排版、基础 AI 改写 | **选题从哪来**。输入仍然是人想好的题目 |
| Taplio 一类 | LinkedIn 的关系与内容管理 | X 上的实时信号，且不做话题加速判断 |
| 直接开 ChatGPT 写 | 单条文本质量 | 没有账号上下文、没有证据链、不知道昨天写过什么 |

缺口在**排序**这一层：从"今天有 40 个话题在动"到"这 3 个值得用我们的身份说"，中间那一步没人做。这个 demo 只做那一步，以及它前后的衔接。

## 3. Product Logic

### 3.1 用户是谁

不是 social media manager，是**自己做分发的 founder / growth lead**。真实状态：

- 每天刷 X，看到一堆热点，但不知道哪个跟自己有关
- 想发，但每次都要从零想角度，一条要 40 分钟
- 发了以后看 likes，但 likes 不等于客户

产品要解决的不是"内容不够"，是**"不知道说什么、说了不知道有没有用"**。

### 3.2 七步闭环，每步的产出物

| 步 | 输入 | 输出 | 人的介入 |
|---|---|---|---|
| Monitor | 14 个账号的公开时间线 | 结构化帖子流 | 配名单 |
| Detect | 窗口内帖子 | 话题簇 + 摘要 + 置信度 | 无 |
| Rank | 话题簇 | 0–100 机会分 + 理由 | 无 |
| Ideate | 选中的话题 | 3 个角度 × 3 个版本 × 3 种格式 | 选角度和格式 |
| Draft | 角度 + 事实 | 一条草稿 + 证据链 | 改 |
| Review | 草稿 | 通过 / 打回 | **必须** |
| Publish | 通过的草稿 | 发到 @telyclaw | 点一下 |
| Measure | 发布结果 | Qualified Engagement | 无 |

### 3.3 三条明确的产品取舍

**① 不做全自动发布。** 需求写的是「内容生成 ≠ 直接发布」，我把它做成硬约束：`Publish` 只在 `approved` 状态出现，且单日上限 4 条——**两个入口（生成页、审核页）共用同一个判定**，因为能绕过去的护栏不叫护栏。不是技术上做不到自动发，是品牌账号自动发一次事故的成本远高于省下 5 分钟。

**② 不做"热点排行榜"。** 纯按互动量排序，出来的永远是最大账号说的话。机会分里相关性占 20% 权重，再加一道 0.4–1.0 的相关性门——不相关的话题热度再高也进不了 Top 3。

**③ 北极星不是发帖数，也不是曝光。** 见 §9。

### 3.4 一个具体的决策例子（demo 里真实存在，数字可复现）

24H 窗口下：

| # | 话题 | 帖子 | 速率 | 相关性 | 分数 | 结论 |
|---|---|---|---|---|---|---|
| 1 | Agent 记忆 | 24 | +21% | 0.88 | 78.9 | 主攻 |
| 2 | AI 自动化增长 | 9 | +40% | 0.96 | 75.4 | 主攻 |
| 3 | MCP 工具生态 | 12 | +86% | 0.81 | 69.8 | 主攻（早期信号） |
| 5 | **Vibe Coding** | **5** | **−33%** | **0.74** | **39.0** | **放弃** |

Vibe Coding 是这个圈子里最响的词，但 24 小时里只有 5 条帖子、速率 −33%、在退潮，跟进去只能重复别人说过的话，排第五。同一时刻「AI 自动化增长」只有 9 条帖子，速率 +40%、相关性 0.96，排第二。

**这就是产品想做的事：在别人还在比谁声音大的时候，看谁在加速。**

## 4. System Architecture

```
┌──────────────────────────────────────────────────────────────┐
│  UI (React 18 + TS, 无 UI 框架, 手写 CSS)                      │
│  Monitor │ Trends │ Opportunity │ Studio │ Review │ Analytics │
└───────────────────────────┬──────────────────────────────────┘
                            │ useEngine() — 单一状态源
┌───────────────────────────▼──────────────────────────────────┐
│  Engine (纯函数, 无副作用)                                      │
│  detect.ts    clusterPosts()  → keyword-anchored 聚类          │
│               buildTrends()   → 窗口聚合 + 五因子 + 三乘数       │
│                               + 排名回放（市场提前量）           │
│  generate.ts  generateDraft() → 角度 × 版本 × 格式              │
│               findDuplicate() → 4-gram Jaccard 护栏             │
│               simulateOutcome() → 发布结果模拟（明确标注）       │
│  metrics.ts   computeMetrics() → 北极星 + 支撑指标               │
│  config.ts    扫描间隔 / 日发上限 / 基线，全站唯一来源            │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  Data                                                          │
│  topics.ts 9 个话题 × 3 个角度 × 3 个版本 × 中英               │
│  seed.ts   14 个账号（全部虚构）                                │
│  corpus.ts 418 条合成帖子，mulberry32 种子 PRNG（可复现）        │
│            互动量按 exp(-age/3h) 累积 —— 新帖不该跟老帖比绝对值   │
└──────────────────────────────────────────────────────────────┘
```

**为什么是纯函数 + 一个 hook。** 没有 Redux、没有 server、没有 ORM。引擎是 `(posts, now, windowHours) → Trend[]`，同一份输入永远得到同一份输出——这是能写测试、能录视频、能被审阅的前提。

**为什么虚拟时钟。** 数据是合成的，所以 `now` 是变量而不是 `Date.now()`。`LIVE ×30` 打开后虚拟时钟每秒走 30 秒，语料里预留的 8 小时"未来帖子"陆续出现，速率和排序实时变化。不用等真实世界，也能演示实时检测。

## 5. Trend Detection Logic

### 5.1 怎么聚

每个话题有一组关键词短语（`context window`、`compaction`、`recall`…）。对每条帖子：

1. 分词，去掉标点
2. 每个关键词的每个词做 **4 字符词干**（`automation` / `automated` 都归到 `autom`）
3. 短语连续命中才算一次，权重 = 短语词数（`context window` 比 `context` 值钱）
4. 取最高分话题；最高分为 0 则归入「未归类」
5. `purity = 最高分 / 所有话题得分之和` —— 一条同时讲三个话题的帖子纯度低，不该被当强信号

当前语料：**准确率 83.1%（310/373），未归类 45 条**。这个数字在监控页和指标页实时显示。

> **这个 83% 要打个折看。** 语料是用每个话题自己的模板生成的，关键词表和语料同源——等于拿同一套词表出题又用同一套词表判卷。它证明的是"聚类没有坏掉"，不证明"能处理真实推文"。真实数据上必须重新评估。

### 5.2 为什么不用 embedding

MVP 阶段 9 个已知话题、418 条帖子，embedding 带来三个成本：一次 API 调用、一个向量存储、一个不可解释的相似度。而关键词锚定的好处是**每个归类都能点开看命中了哪几个词**——需求里"输出 Summary / 关键词 / 代表性帖子"这一条，关键词锚定天然满足。

生产怎么换：`text-embedding-3-small` 或本地 bge-m3 做向量，HDBSCAN 无监督聚类，话题不预设、自动长出来；关键词降级为"给聚类结果命名"的工具。`clusterPosts()` 是唯一需要替换的函数，签名不变。

### 5.3 窗口聚合

每个话题在每个窗口算 9 个量：

| 量 | 含义 |
|---|---|
| `posts` / `accounts` | 体量与参与面（1 个账号发 20 条 ≠ 20 个账号发 1 条） |
| `engagement` | 加权互动：赞 1 / 转 2 / 评 3 / 藏 1.5 / 引用 2 |
| `prevEngagement` | 上一个等长窗口，用来算速率 |
| `velocityRatio` | 速率比，带先验平滑（见 §6.2） |
| `meanAgeHours` | 平均帖龄，喂给 freshness |
| `keywordCoverage` | 命中关键词 / 全部关键词 = 角度覆盖度 |
| `duplicateRatio` | **跨账号**近似重复比例（4-gram Jaccard > 0.5） |
| `purity` | 聚类纯度均值 |
| `prevAvailable` | 上一个窗口是否落在语料内 |

`duplicateRatio` 只统计"不同账号之间的重复"。同一账号重复自己是发帖习惯，不同账号重复同一句话才是话题饱和的信号。

### 5.4 阶段判定

| 阶段 | 条件 | 该做什么 | 推荐角度 |
|---|---|---|---|
| 早期信号 | 速率 > 1.45× 且帖子 < 16 | 占位，成本最低 | 拆解复盘（先立专业度） |
| 上升 | 速率 > 1.15× | 主攻 | 产品视角 |
| 平台期 | 0.85× – 1.15× | 观察 | 产品视角 |
| 已饱和 | 跨账号重复 > 70% 且速率 < 1.25× | 放弃，除非有独家角度 | 反共识一句话 |
| 退潮 | 速率 < 0.85× | 只值一句评论 | 反共识一句话 |
| 样本不足 | 帖子 < 3 | 不下判断 | — |

## 6. Opportunity Ranking Logic

### 6.1 公式

```
baseScore = 100 × ( 0.30·velocity
                  + 0.20·momentum
                  + 0.20·relevance
                  + 0.15·freshness
                  + 0.15·contentOpportunity )

score = baseScore × relevanceGate × sampleShrink × learnedFactor
```

| 因子 | 权重 | 怎么算 | 为什么 |
|---|---|---|---|
| **Trend Velocity** | 0.30 | `0.5 + log₂(速率比)/2`，夹到 [0,1] | 加速度比绝对值重要。爆了三天的热点，进去只剩残羹 |
| **Engagement Momentum** | 0.20 | 窗口内互动率的对数归一化 | "现在有多大声" |
| **TelyClaw Relevance** | 0.20 | 人工设定，每周复核 | 不相关的高热度 = 噪音 |
| **Freshness** | 0.15 | `exp(-平均帖龄 / 0.8×窗口)` | 越新的讨论越值得介入 |
| **Content Opportunity** | 0.15 | `0.55×角度覆盖 + 0.45×(1−重复度)` | 覆盖度高=有多个切入角度；重复度高=没位置了 |

三个乘数（详情面板里逐项可见）：

| 乘数 | 范围 | 作用 |
|---|---|---|
| `relevanceGate = 0.4 + 0.6·relevance` | 0.64 – 0.98 | 相关性低的话题被压低，但不直接判死（0.42 的开源模型话题仍能被看到，只是排不进前三） |
| `sampleShrink` | 0.15 – 1.0 | 1 条帖子不该打赢 20 条；窗口内 0 条帖子时压到 0.15，不让相关性单独把它抬上去 |
| `learnedFactor = 0.9 + 0.2·历史命中率` | 0.9 – 1.1 | 闭环的入口，见 §9 |

### 6.2 两个必须处理的数值坑

**① 上一窗口为 0 时，速率会爆。** 第一版做出来 1 小时窗口里某话题显示 `386×`——因为前一个小时是 0，任何一条帖子都是无限加速。修法是加先验：`(rateNow + prior) / (ratePrev + prior)`，`prior = 全部话题速率均值的一半`。加完同一场景是 `2.5×`，仍然领先，但不再是噪声。

**② 7D 窗口根本没有"上一个 7 天"。** 语料只有 7 天，`prevAvailable=false`，速率按中性 0.5 处理，界面明写「上一窗口无数据，速度按中性处理」。第一版这里还有个连带 bug：中性速度让"重复度高"的判定条件恒成立，9 个话题全被标成"已饱和"。修法是给那个判定加上 `prevAvailable &&`。装作有数才是错的。

### 6.3 排序要能点开

详情面板里五个因子条 + 八个辅助量（速率比、平均帖龄、关键词覆盖、重复度、纯度、相关性门、样本收缩、历史命中修正）。每个都直接对应公式里的一项，没有"AI 觉得"。

## 7. Content Generation Logic

### 7.1 三个角度是三种"发言位置"

| 角度 | 什么时候用 | 结构 |
|---|---|---|
| **反共识观点** Hot Take / Opinion | 话题已有主流叙事，或已经饱和 | 否定主流 → 数据 → 我的判断 |
| **拆解复盘** Educational / Insight | 话题需要可信度，或处于早期 | 具体动作编号 → 数据 → 哪一步最关键 |
| **产品视角** TelyClaw Product Angle | 话题与产品强相关 | 把公共话题翻译成产品能解决的具体问题 |

需求给的三个名字是 Hot Take / Educational / Product Angle。我把它落成「反共识 / 拆解复盘 / 产品视角」，因为 Educational 在 X 上不是"科普"，是"把一件事拆开讲清楚，让人能照着做"——所以它的结构里必须有可执行的动作编号，光有观点不算这一档。

角度不是随机给的：系统按阶段标一个「推荐」（饱和→反共识，早期→拆解，其余→产品视角），但三个始终都在，因为**"这个题该用什么姿势说"最终还是人的判断**。

### 7.2 三个版本 × 三种格式

需求要求"每个角度至少 3 条不同版本"，并且"内容长度可扩展 Copy / Rewrite / Summary"。这两件事是正交的：

- **版本**换的是论点入口。v0 完整论证，v1 换一个切入角度，v2 短打（只留最锋利的一句）。每个角度中英各 3 条，全部手写，不是同义改写。
- **格式**换的是结构：
  - `Copy` — 单条，在句子边界裁到 240 字符，hashtag 只在放得下时加
  - `Rewrite` — 引用窗口内互动最高那条帖子，再接我们的观点（引用转发是这个平台上最自然的"我有不同看法"）
  - `Summary` — 完整论证 + 三条编号补充，数据全部来自当前窗口

3 角度 × 3 版本 × 3 格式 = 27 种产出，同一个话题。

### 7.3 事实注入

草稿里那句带括号的数据行不是模板占位符，是**运行时算出来的**：

```
(7 accounts we track posted about it 24 times in 24h. Engagement rate +21% vs the previous window.)
```

生成器只允许引用**当前窗口内互动排名前 3 的帖子**作为证据（Studio 右侧"证据链"）。这条约束的意义是：不给生成器编造"看起来像数据"的句子留口子。

### 7.4 双语

UI 中文（给评审看），草稿默认英文（X 是全球流量池，也是出海产品的默认语言），可一键切中文。两套模板独立撰写，不是机翻。

### 7.5 护栏：重复检测

发布前用 4-gram Jaccard 比对所有已通过/已发布草稿，相似度 > 45% 就警告：

> 相似度 68% · 与已发布内容高度重合，建议换角度而不是换措辞。

同一个话题反复发同样的句子，在 X 上会被判重并降权——这个护栏不是体验优化，是账号安全。

### 7.6 生产环境接 LLM 怎么接

`generateDraft()` 是唯一需要替换的函数。Prompt 骨架：

```
你是 TelyClaw 的内容负责人。基于以下事实写一条 X 帖子，不要编造数据。

事实：
- 话题：{topic}
- 窗口数据：{stats}
- 三条代表性帖子：{evidence}
- TelyClaw 的品牌资产：{brandAsset}
- 角度：{angle} / 格式：{format}

约束：
- 必须包含一条来自上述事实的具体数字
- 不得使用"赋能/闭环/抓手"这类词
- 输出 JSON：{ text, claims[] }，claims 逐条对应事实编号
```

`claims[]` 是给审核的人看的：这句话依据哪条事实。没有 claims 的句子，审核员可以直接删。

## 8. Human-in-the-loop

四个状态，每一步都有记录：

```
AI Draft ──(编辑)──> Human Edit ──(Approve)──> Approved ──(Publish)──> Published
```

- **改写率**实时计算（Levenshtein / 原文长度）。改写率 > 50% 说明角度选错了，不是措辞问题——这个数字会进 `simulateOutcome` 作为惩罚项
- **单日发布上限 4 条**，生成页和审核页共用同一个判定，超了两边都禁用
- **Publish 只在 Approved 状态出现**，代码里没有旁路

## 9. 指标体系

### 9.1 北极星

**Qualified Engagement per Published Post** = 已发布内容带来的有效互动 / 已发布条数

- **Qualified = ICP 账号带来的互动**：自建产品、自己做分发的 Dev Tool / Indie Builder / Growth Operator。AI Lab 和媒体的高互动不计入——**流量大不等于客户**
- 基线 3，demo 初始状态 4.2，命中率 80%

为什么不选曝光：曝光可以买，可以蹭大账号，可以和生意毫无关系。为什么不选发帖数：那是在奖励勤奋，不是奖励效果。

### 9.2 支撑指标

| 指标 | 目标 | 当前值 | 性质 | 判定 |
|---|---|---|---|---|
| 检测延迟（扫描间隔） | < 30 min | 15 min | **设计值**，不是测量值 | ✅ |
| Trend Hit Rate | > 50% | 80%（4/5） | 模拟结果 | ✅ |
| Acceptance Rate | > 50% | 86%（6/7） | 真实计数 | ✅ |
| Trend → Content Time | 需求建议 5–10 min；我们的验收线 < 30 min | 25 min（中位数） | 真实计数（时间戳） | ✅ 达标，未达需求建议值 |
| Engagement Lift | > 1× | 1.4×（21 有效互动 / 5 条 / 基线 3） | 模拟结果 | ✅ |
| 北极星 | — | 4.2 | **模拟结果** | 参考 |

> 加粗那几行必须分开看：**扫描间隔**是配置；**命中率、Lift、北极星**来自 `simulateOutcome()`，是模型输出，不是市场反馈；**Acceptance Rate 和 Content Time** 是真实计数（前者数状态，后者算时间戳）。

**Trend → Content Time 为什么是 25 分钟，不是 5–10 分钟。** 机器那一段（检测 → 三个角度 → 草稿）不到 1 分钟，25 分钟里 24 分钟是人改写和审批。要压到 10 分钟只有两条路：LLM 出稿质量高到不用改，或者允许不审直接发。前者模板生成做不到（§12.1），后者我明确不做（§3.3 ①）。所以这里报 25 分钟——报一个靠"跳过审稿"凑出来的 8 分钟，比报 25 分钟更不可信。

**市场提前量**是另一个数，不进达标表：话题首次进入 Top-3 的时刻，减去它小时互动量达到 7 日峰值一半的时刻。正数=我们早，负数=已经过峰。它用 1 小时粒度回放、且回放时的排序是简化版（只用速率×相关性近似，没有跑完整机会分），所以是参考量。demo 里 Top-3 有两个是负的——这不是 bug，是"24 小时窗口下确实会捞到已经过峰的话题"，也说明排序还该把"过峰"当成一个惩罚项，见 §12.2。

### 9.3 闭环怎么闭上

```
发布 → 量 Qualified Engagement → 话题命中率 → learnedFactor (0.9×–1.1×) → 下一次排序
```

幅度故意做得小。单条内容的成败不足以推翻一个话题的判断，但连续 5 条都在这个题上失败，0.9× 会把它挤出主攻名单。指标页的「话题级表现」表就是这个反馈的账本。

## 10. 数据说明：为什么是 mock，以及真要上线怎么接

### 10.1 现状

- **418 条合成帖子**，14 个**虚构**账号，7 天 + 8 小时
- 用 `mulberry32(20261104)` 固定种子，每次刷新数据完全一致（录视频不会变）
- 账号名、bio、互动量全部是编的。**没有一条真实推文被伪造或引用**

不接真实数据的原因有两个，第二个更重要：

1. X API 现在按量计费，跑通需要付费账号
2. 更关键的是——**用真实账号的 handle 配假推文，等于伪造他人言论**。宁可数据假，不能把假话挂在真人名下

### 10.2 真实数据怎么拿，以及一个月多少钱

X 在 2026 年 2 月把 API 改成按量计费（[developer.twitter.com](https://developer.twitter.com/) 现在写的是 consumption-based billing，无固定月费、无月度上限），约 **$0.005 / 条读取，$0.01 / 条发布**。单价以官方定价页为准，下面的账按这个数量级估算。

假设：14 个账号、每账号每天 2 条新帖（demo 语料里是 4.3 条/天，偏高，真实账号更接近 1–3 条）。

| 环节 | 做法 | 量 | 日成本 |
|---|---|---|---|
| 增量采集 | `GET /2/users/:id/tweets` + `since_id`，只取新增 | 28 条/天 | $0.14 |
| 指标回填（1h 一次） | 近 24h 帖子每小时刷 `public_metrics` | 28×24 = 672 次/天 | $3.36 |
| 发布 | `POST /2/tweets` | 4 条/天 | $0.04 |
| **合计** | | | **≈ $3.5/天 ≈ $105/月** |

关键发现在**回填频率**这个旋钮上，不在采集：

| 回填频率 | 月成本（14 账号） | 月成本（200 账号） |
|---|---|---|
| 每 1 小时 | ≈ $105 | ≈ $1,450 |
| 每 6 小时 | ≈ $18 | ≈ $240 |

**6 倍的差别。** 所以定价必须建在这个旋钮上：如果按 $99/月/工作区卖，1 小时回填的数据成本就吃掉全部收入，毛利为负；要么按账号数加价，要么把回填降到 6 小时并接受"发布后 6 小时内看不到趋势"。这是产品定价问题，不是工程问题。

### 10.3 如果明天就要进 Production

1. **采集层**：worker + Redis 队列，按账号分片，`since_id` 存 DB 做断点续传；指数退避处理 429；用 `/2/tweets/search/recent` 兜底补齐漏采
2. **存储**：Postgres，`posts(account_id, tweet_id, created_at, metrics_json)`，按 `created_at` 分区；互动量存时序快照而不是覆盖写
3. **聚类**：换 embedding + HDBSCAN（§5.2）
4. **生成**：接 Claude / GPT，用 §7.6 的 prompt，`claims[]` 强制结构化输出
5. **发布**：OAuth 2.0 user context，发布前二次确认，失败重试 + 告警
6. **合规**：只读公开数据；不做大规模抓取；用户可随时删除自己的数据

## 11. AI / Vibe Coding 工具

用 **WorkBuddy** 完成（需求给的两个选项之一）。不是"生成一个网站"，是把 AI 当执行层，人负责判断。

| 环节 | 我做的判断 | AI 做的执行 |
|---|---|---|
| 选题与话题库 | 定 9 个话题、每个的相关性分数与理由；否掉"再加 5 个话题"的提议——话题越多，每个的质量越低 | 写模板、生成语料 |
| 排序公式 | 定权重、定三乘数、定先验平滑 | 实现、跑 `npm run check` 逐窗口对比 |
| 数值调试 | 发现 386× 速率异常，判定是先验问题；发现 7D 全判饱和，判定是 `prevAvailable` 漏了 | 改公式、重跑、对比四组窗口 |
| 界面 | 定信息层级：分数→理由→证据→动作；否掉第一版的"大图表仪表盘"——用户要的是决策，不是监控大屏 | 写组件、写 CSS |
| 测试 | 定"必须真点一遍"的标准 | 写 CDP 脚本，跑 19 项断言 |
| 验收自查 | 逐条比对需求原文，发现漏了"每角度 3 个版本"和"Copy/Rewrite/Summary"两项 | 补 162 条模板、加格式层 |

**AI 给错而我否掉的，具体有三处：**

1. 第一版排序没有先验平滑，1 小时窗口出现 386× 加速。AI 的修法是"加个上限截断"，我否掉了——截断会掩盖问题，先验才是对的。
2. 第一版把"每个角度只保留一个模板"当成够用。实际需求写的是每个角度 3 个版本，这是漏项，不是取舍。
3. 第一版指标页有一个手写的 sparkline（假数据占位）。我让它删掉换成真实序列——指标页出现假曲线，整页的可信度就没了。

值得说的一点：**排序引擎的第一版是错的**。这种错只有把数字打出来看才会发现，光看界面看不出来——所以有了 `scripts/check.ts`。

## 12. MVP 边界与下一步

### 12.1 这个 MVP 故意不做的

| 不做 | 为什么 |
|---|---|
| 真实 X API 接入 | §10，成本 + 伪造风险 |
| 多租户 / 登录 | 验证闭环不需要 |
| 真正的 LLM 生成 | 模板化生成已经能验证"角度是否成立"，接 LLM 是替换一个函数（§7.6） |
| 定时任务 | 虚拟时钟已经能演示实时性 |
| 移动端适配 | 这是个工作台，桌面优先 |

### 12.2 如果继续做，优先级

1. **接真实数据 + 真实 LLM**（1 周）——把 §10.3 和 §7.6 落地，其他不动
2. **给"过峰"加惩罚项**（2 天）——现在 Top-3 里有已经过峰的话题（§9.2），说明 freshness 的衰减不够狠。把"距峰值时长"直接进公式，比调权重更有效
3. **角度效果归因**（1 周）——现在只知道"这个话题有效"，不知道"反共识角度是不是比拆解角度好"。按 `angle × topic` 二维统计，这是最能提升命中率的一件事
4. **竞品内容缺口**（2 周）——现在只回答"什么在火"，没回答"什么该火但没人写"。做法：话题 × 角度矩阵里空白的格子
5. **多平台**（2 周）——LinkedIn / Reddit 的同一套信号，`detect.ts` 不用改，只换采集层

### 12.3 已知限制

- **模拟结果的循环论证**：`simulateOutcome()` 让机会分高的话题拿到更好的结果，所以"高分话题命中率更高"部分是设计出来的，不是发现的。真实数据进来后必须重估，这也是为什么 §9.2 把北极星标成"模拟结果"
- **聚类准确率不能外推**：语料与关键词同源（§5.1）
- **7D 窗口算不出速率**：语料只有 7 天，界面已标注
- **市场提前量是近似回放**：1 小时粒度，且回放排序是简化版（§9.2）
- **互动量累积模型是假设**：`exp(-age/3h)`，真实曲线更接近双峰
- **排序权重是手调的**：没有用真实数据拟合过。样本量不够时，手调比拟合诚实

## 13. 附录：怎么自己验一遍

```bash
npm run dev
```

1. 顶栏切 `1H` → 九个话题里有五个掉到个位数（窗口内 0 条帖子，样本收缩直接压到 0.15）。只有一小时里真在动的还留在榜上：Agent 记忆 50.6（2 条帖子、速率 17×）、AI 产品定价 30.7。一小时窗口只够看"有没有在动"，不够下结论
2. 切回 `24H` → Top 3 是 Agent 记忆 / MCP / AI 自动化增长
3. 打开 `LIVE ×30` 等 30 秒 → 时钟前进，速率与排序会变
4. 进「机会排序」→ 看最下面「我们主动放弃的」，每条都有具体理由
5. 进「内容生成」→ 切格式 Copy / Rewrite / Summary，同一个角度出三种长度
6. 点 Hot take → 用「变体 +」换版本，三次文本不同
7. 改两句 → Approve → Publish → 等 1.5 秒出结果
8. 回「审核队列」→ 状态轨走到 Publish
9. 进「指标闭环」→ 北极星和话题级表现表已经把你刚发的那条算进去了

`npm run e2e` 会把 5–8 步自动跑一遍，19 项断言。
